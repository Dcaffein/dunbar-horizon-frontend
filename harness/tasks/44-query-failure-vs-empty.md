# Task 44: 조회 실패와 "데이터 없음" 구분

> 미착수. Task 42(실패 정규화) 완료가 전제다.

## 문제

조회 Server Action 15곳이 실패를 빈 배열로 삼킨다.

```ts
catch { return { success: false as const, data: [] as FlagResult[] }; }
```

화면에는 `"참여중인 Flag가 없습니다"`가 뜬다. **사용자는 빈 화면을 사실로 믿는다.**
재시도할 방법도, 뭔가 잘못됐다는 신호도 없다.

Task 41 검증에서 실제로 이 함정에 걸렸다. 프로필의 최근 Flag가 비어 보였는데
화면만으로는 "조회 실패"인지 "그 친구에게 Flag가 없음"인지 알 수 없어,
API를 직접 호출해서야 후자임을 확인했다.

## 대상 15곳

```
flag.ts:21,31,44,54,159,169,236,248,290
buzz.ts:21,134   label.ts:15,27   notification.ts:15   social.ts:100
```

`{ silent: true }`가 붙은 곳은 로그조차 남지 않는다.

## 방향

`ApiError.kind`로 갈라 화면이 다르게 반응하게 한다.

| `kind` | 화면 |
|---|---|
| `network` · `timeout` | "연결을 확인해 주세요" + **재시도 수단** |
| `http` · `parse` | 사유 표시. 재시도는 상황에 따라 |
| 성공 + 빈 배열 | 지금의 빈 상태 문구 (진짜 "없음") |

## 범위가 큰 이유

액션만 고쳐서는 끝나지 않는다. **화면마다 실패 상태를 어떻게 보여줄지 결정**해야 한다 —
전체 화면인지 인라인인지, 재시도 버튼을 어디 두는지, 부분 실패(메인 그래프처럼
여러 조회를 병렬로 하는 곳)를 어떻게 표현하는지.

특히 [app/page.tsx](src/app/page.tsx)는 `Promise.all` + 개별 `.catch()`로
여러 조회를 병렬 처리한다. 하나가 실패했을 때의 표현이 별도 설계 대상이다.

착수 전에 실패 상태 UI 패턴을 먼저 정하고, 그 다음 액션 시그니처를 맞춘다.
