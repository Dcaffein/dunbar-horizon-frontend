# Task 51: 백엔드 오류 코드 계약 소비와 화면 정합성

## 목표

백엔드의 93개 안정 오류 코드를 프론트 계약에 반영한다. 서버 `message`는 화면의
정본으로 사용하지 않고, 프론트가 코드와 전송 실패 종류에 따라 사용자 문구를 소유한다.

## 범위

- `ApiErrorCode`를 최종 93개 표와 동기화하고, 이전 포괄 코드를 제거한다.
- `Failure`가 `code`를 직렬화해 Server Action과 Client Component 사이에서 보존한다.
- Flag 초대 수락이 `FLAG_NOT_RECRUITING`으로 실패하면 목록을 재조회해 무효 카드를 제거한다.
- 409마다 재조회하지 않는다. 참여/참여 취소는 실제 상태가 화면과 달라지는 코드만 후속 검증에서 추가한다.

## 문구 정책

서버 `message`는 내부 식별자, 프레임워크 기본 영문, 릴리스별 문구 변경을 포함할 수 있다.
따라서 원문은 `ApiError.detail`에만 남기고, 화면에는 프론트 소유 문구만 전달한다.
필드별 `validation` 바인딩은 Task 45에서 다룬다.

## 검증 결과

### Phase 1 — 통과

- 아티팩트의 93개 코드와 `ApiErrorCode` 유니온을 대조했다.
- `npm test -- --run src/api/apiClient.test.ts` — 7/7 통과.
- `npx tsc --noEmit` — 통과. `npm run lint`는 기존 3 errors/11 warnings와 동일하며,
  이번 변경 파일에서는 새 진단이 없다.
- 실행 코드에는 Java 예외 클래스명/이전 포괄 코드 분기가 없다. 남아 있는 문자열은
  계약 변경의 배경을 설명하는 주석과 원문 비노출 단위 테스트뿐이다.

### Phase 2 — 계약 배포 대기

- 두 테스트 계정으로 임시 Flag를 생성해 초대를 시도했으나, 현재 로컬 백엔드는
  `409 FLAG_INVALID_STATUS`를 반환했다. 아티팩트의 최종 계약에는 없는 이전 포괄 코드다.
- 따라서 아티팩트의 세분화 계약은 이 로컬 서버에 아직 배포되지 않았다. 같은 서버에서
  `FLAG_NOT_RECRUITING` 경쟁 상태를 실측할 수 없으므로 최신 백엔드 배포 전까지 보류한다.
- 임시 Flag는 `204`로 정상 삭제했다. 초대는 생성되지 않았고 데이터가 남지 않았다.
- `FLAG_NOT_RECRUITING` 처리 자체는 컴포넌트 단위에서 검증했다. 수락 실패 시 카드 제거,
  안내 표시, `router.refresh()` 호출을 확인했고 다른 409는 카드를 유지한다.
- 로컬 브라우저 자동화는 CDP 연결 오류로 DOM 검증을 진행하지 못했다.

### Phase 3 — 부분 통과

- 현재 참여 중인 종료 Flag에 중복 참여를 요청해 `409 FLAG_PARTICIPATION_DUPLICATE`를
  실측했다. 이미 참여자로 보이는 화면은 사실과 맞으므로 재조회를 추가하지 않는다.
- 같은 응답의 서버 `message`에는 사용자·Flag ID가 포함돼 있었다. 원문 비노출 정책이
  현재 배포 백엔드에서도 필요함을 확인했다.
- `FLAG_NOT_RECRUITING`, `FLAG_FULL_CAPACITY`, `FLAG_RECRUITMENT_CLOSED`의 실제
  화면 변화를 확인하려면 경쟁 상태를 만들 수 있는 초대/두 번째 테스트 계정이 필요하다.
