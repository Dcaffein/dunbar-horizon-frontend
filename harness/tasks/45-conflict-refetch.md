# Task 45: 409를 문구가 아니라 재조회로 처리

> 미착수. Task 42(실패 정규화) 완료가 전제다.

## 문제

409 Conflict는 **"당신이 보고 있는 데이터가 이미 바뀌었다"**는 뜻이다.
그런데 지금은 문구만 띄우고 끝나서, 안내를 읽은 뒤에도 **화면은 여전히 틀린 상태**를 보여준다.

Task 41에서 확인된 사례:

| 상황 | 지금 |
|---|---|
| 종료된 Flag에서 참여 취소 | 문구 표시. 참여자 목록은 그대로 |
| 만료된 초대 수락 | 문구 표시. 초대 카드가 목록에 남아 있음 |

두 번째가 특히 어색하다. 이미 유효하지 않은 초대인데 목록에 남아 있어
사용자가 다시 누를 수 있다.

## 방향

`status === 409`면 문구를 띄우기 **전에** 관련 상태를 다시 가져온다.

```
409 → 해당 리소스 재조회 → 화면 갱신 → 그다음 안내
```

낙관적 업데이트를 쓰는 화면에서는 되돌리기(rollback)도 함께 검토한다.

- [FlagInvitationList.tsx](src/components/Flag/FlagInvitationList.tsx) — 초대 수락·거절

## 선행 확인

409를 내려주는 엔드포인트 목록과 각각의 의미를 먼저 정리해야 한다.
모든 409가 "재조회하면 해결"인 것은 아니다 —
"이미 처리됨"과 "상태가 안 맞음"은 대응이 다를 수 있다.

`code`(예외 클래스명)로 구분하고 싶어질 수 있으나 **그 방향으로 가지 않는다.**
클래스명은 계약이 아니라 구현 세부다(Task 42 참고). 구분이 정말 필요하면
백엔드에 안정적인 code 계약을 요청한다.
