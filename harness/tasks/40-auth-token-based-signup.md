# Task 40: 토큰 기반 회원가입 플로우 전환

## 배경

백엔드가 회원가입 방식을 **"가입 후 인증"에서 "인증 후 가입"으로 역전**했다.
API 명세서(`/v3/api-docs`) 재생성 결과 `account-controller`에 아래 변경이 반영되어 있다.

| 엔드포인트 | 변경 | 내용 |
|---|---|---|
| `POST /api/auth/verifications` | 이름 변경 | `sendVerificationEmail` → `requestVerification`. body는 동일 |
| `GET /api/auth/verifications/{token}` | **신규** | `VerificationTokenResponse { email? }` 반환. **토큰을 소비하지 않는 유효성 확인용** |
| `PATCH /api/auth/verifications?token=` | **삭제** | 별도의 "인증 확정" 단계가 사라짐 |
| `POST /api/auth/users` | DTO 변경 | `SignupRequestDto.email` → **`token`** |

이메일 소유 증명은 **Redis의 `token → email` 매핑**으로 표현된다. 링크 클릭은 토큰을 소비하지 않고,
실제 소비(GETDEL)는 가입 시점에 일어난다. 결과적으로 **가입과 이메일 인증이 하나의 트랜잭션**이 되고,
**미인증 회원 레코드라는 상태가 사라진다.**

## 목적

현재 프론트는 구 계약을 전제하고 있어 세 지점이 깨져 있다.

- `signupAction` — `email`을 보내고 `token`이 없어 **400**
- `verifyEmailAction` — 삭제된 `PATCH` 호출로 **404**
- 로그인 `UNVERIFIED` 분기 — 미인증 계정이 존재할 수 없으므로 **도달 불가 코드**

이를 신규 계약에 맞추고, "인증 → 가입 → 자동 로그인"이라는 바뀐 흐름을 UI로 표현한다.

## 확정된 백엔드 계약

### `POST /api/auth/users` 응답

| 상황 | status | 비고 |
|---|---|---|
| 성공 | **201** | 본문 없음, **쿠키 2개 발급 = 자동 로그인** |
| `token` 누락 / 비밀번호 규칙 위반 | 400 | `{ error, validation }` — `message` 키 없음 |
| 토큰 만료 · 미존재 | 410 | `InvalidVerificationTokenException` |
| 이미 가입된 이메일 | 409 | `AlreadyRegisteredEmailException` |

### 토큰 정책

- **재발송해도 이전 토큰은 무효화되지 않는다.** 같은 이메일에 유효한 링크가 여러 개 공존하며 상한은 **TTL 1시간**뿐이다.
  레이트 리밋도 없다. "재발송 시 이전 링크 무효화"가 직관적이지만, 공격자가 피해자 주소로 반복 접수하면
  **피해자의 인증이 영구적으로 불가능해지는** DoS가 되기 때문에 의도적으로 피한 설계다.
- 토큰 A로 가입을 마친 뒤 남은 토큰 B를 제출하면 → B의 Redis 키는 살아 있어 `GETDEL`이 성공하고(B도 이때 소비됨),
  `findByEmail` 검사에 걸려 **409**가 된다. **410이 아니다.**
- 이미 가입된 이메일로 인증을 접수해도 **응답은 201로 동일**하다. 토큰을 만들지 않고 안내 메일만 발송하며,
  구분은 **메일 내용으로만** 이루어진다(가입 링크 vs "이미 가입된 계정입니다" 안내). 계정 열거 방지가 목적이다.
  → `/signup` 안내 문구를 "이미 가입된 계정이라면 로그인 안내 메일이 갑니다"로 보완한다.
  메일이 안 온다는 뜻이 아니라 **다른 메일이 간다**는 뜻이다.

### OAuth

`/oauth2/authorization/google` → 백엔드가 `email_verified` 클레임을 검증하고 계정을 자동 생성한 뒤 쿠키를 발급한다.
닉네임은 구글 `name`을 사용하며 **중복을 허용**한다(중복 검사 API 불필요).
쿠키 도메인 공유 방식이므로 콜백 Route Handler도 필요 없다(`6688f8f`에서 이미 제거).
성공 경로는 **프론트 변경 없음.**

### OAuth 실패 리다이렉트 — 신규 작업

지금까지 OAuth 실패는 백엔드 도메인에서 401 JSON 원문이 노출된 채 끝났다.
이제 **프론트로 리다이렉트**되므로 `/login`이 이를 받아 처리해야 한다.

| 리다이렉트 | 화면 문구 |
|---|---|
| `/` | — (성공) |
| `/login` (쿼리 없음) | **문구 없음.** 사용자가 동의 화면에서 취소한 것이라 오류가 아니다 |
| `/login?error=email_not_verified` | "구글에서 이메일 인증이 완료되지 않은 계정입니다" |
| `/login?error=failed` | "로그인에 실패했습니다. 잠시 후 다시 시도해주세요" |

`error` 값은 위 둘 외에는 오지 않는다. 모르는 값은 `failed`와 동일하게 처리한다.
리다이렉트 경로 `/login`은 현재 라우팅과 일치하므로 백엔드에 변경 요청할 것이 없다.

### 기타 정책

- **로그인 실패는 무조건 401 + 동일 본문**이다. 미가입 / 구글 전용 계정 / 비밀번호 불일치를 구분하지 않는다.
  기존 404·409·500 분기를 전부 제거하고 401 단일 처리로 바꾼다 (계정 열거 방지)
- 미인증 계정은 서비스 내에 존재할 수 없다 → `UNVERIFIED` 관련 분기·UI 전부 제거
- 닉네임은 **`1~20`자로 통일**. 좁히는 선택지는 없다 — DB 컬럼이 `varchar(20)`이고,
  10자로 줄이면 이름이 긴 구글 사용자의 가입이 막힌다
- 토큰 재발급 실패 계약(401 통일 / 재사용 감지 403)도 함께 변경되었으나 **Task 39 범위**다

## 설계 결정

### 1. 자격증명 폼은 `/verify-email` 라우트를 재사용한다

기존 라우트를 그대로 쓰고, 역할만 "인증 결과 표시"에서 "가입 완료 폼"으로 바꾼다.

### 1-1. 메일 링크는 origin까지만 백엔드가 정한다 — `redirectPage` 폐기

**백엔드가 프론트 페이지 경로를 알아야 하는 구조를 없앤다.**

`FRONTEND_BASE_URL`은 DNS이자 CORS 허용목록에 이미 등록된 **인프라 설정**이지만,
`/verify-email`은 프론트 라우팅이 바뀌면 함께 바뀌는 **구현 detail**이다. 같은 등급의 상수가 아니다.
백엔드가 후자를 들고 있으면 프론트 라우트 하나를 바꿀 때마다 양쪽 배포가 묶인다.

그래서 메일 링크를 **origin + 쿼리 파라미터**까지만으로 구성한다.

```
https://{FRONTEND_BASE_URL}/?verifyToken=abc
```

백엔드가 아는 것은 origin(이미 CORS에 있는 값)과 `verifyToken`이라는 이름뿐이다.
**어느 화면으로 보낼지는 프론트 미들웨어가 결정한다.** 라우팅을 바꿔도 백엔드는 영향을 받지 않는다.

이 결정으로 `redirectPage`는 존재 이유가 사라진다. 프론트는 더 이상 값을 보내지 않고,
백엔드는 DTO에서 필드를 제거한다.

**이전 플로우로 되돌아갈 수는 없다.** 과거에는 메일 링크가 백엔드 API를 가리켰는데,
그때는 링크 클릭이 곧 인증 완료였기 때문에 가능했다. 지금은 링크를 누른 뒤 사용자가 닉네임·비밀번호를
입력해야 하므로 반드시 프론트 페이지에 도달해야 한다. 백엔드로 보내고 302로 넘기는 방식은
302 목적지 상수가 여전히 필요해 결합이 그대로 남고 리다이렉트만 한 번 늘어난다.

### 2. 409 안내 문구에 "구글"을 넣지 않는다 — 백엔드 제안과 다름

백엔드 전달사항은 409 문구로 "이미 구글로 가입된 이메일입니다"를 제안했으나 **채택하지 않는다.**

409는 두 경로에서 나온다 — 구글이 선점한 경우와, **사용자 자신이 다른 링크로 이미 가입을 마친 경우**다.
후자는 백엔드가 확인해준 동작에서 직접 따라 나온다. 토큰 A로 가입을 마친 뒤 남은 토큰 B를 제출하면
B의 `GETDEL`이 먼저 성공하고 `findByEmail` 검사에서 409가 난다. 구글은 개입하지 않는다.

응답이 동일해 프론트는 둘을 구분할 수 없고, 후자에게 "구글로 로그인하세요"는 틀린 안내다.
따라서 양쪽에 모두 맞는 **"이미 가입이 완료된 이메일입니다. 로그인해 주세요."**로 통일한다.
`/login`에 이메일·구글 두 수단이 모두 있으므로 사용자가 선택하면 된다.
"다시 시도"를 유도하지 않는 점은 백엔드 안내와 동일하다 — 409를 받은 링크는 이미 소비되어 죽어 있다.

### 3. "재발송"이라는 별도 개념을 두지 않는다

링크가 만료됐다는 것은 **가입 절차를 처음부터 다시 밟아야 한다**는 뜻이다.
그리고 재발송과 재시작은 실제로 같은 동작이다 — 둘 다 `POST /api/auth/verifications { email }` 한 번이고
결과도 새 링크 한 통으로 동일하다. 별도의 재발송 UI를 유지할 이유가 없다.

따라서 만료·무효 화면은 **`/signup`으로 돌려보낸다.** 기존 `ResendTicket` 컴포넌트는 삭제한다
(현재 어디서도 import되지 않는 죽은 코드다).

"다시 보내기"가 의미를 갖는 곳은 `/signup` 제출 직후의 발송 안내 화면 하나뿐이다.
여기서는 사용자가 방금 이메일을 입력했으므로 재입력 없이 같은 액션을 한 번 더 호출하면 된다.
이 버튼에 쿨다운을 둔다 — 근거는 링크 보호가 아니라 **메일 남발 방지**다(이전 링크도 그대로 유효하다).

안내 문구에는 **"이전 링크는 사용할 수 없습니다" 류를 넣지 않는다.**
사용자가 알아야 할 것은 "이전 것이 죽었는지"가 아니라 **"언제까지 유효한지(1시간)"**다.

### 4. 백엔드 예외 메시지를 화면에 그대로 노출하지 않는다

Task 05에서 세운 원칙과 동일하다. 특히 409 본문에는 이메일 전체가 담겨 오지만 사용하지 않는다.
계정 열거 방지 목적이 아니라(사용자가 직접 입력한 주소다), 원문에는 **사용자가 할 일**이 없고
문구가 백엔드 구현에 종속되기 때문이다. 단 400의 `validation` 값은 필드 단위 입력 안내이므로 예외로 둔다.

## 백엔드 미해결 (프론트 착수를 막지 않음)

### ~~`redirectPage` 오픈 리다이렉트~~ → 설계 결정 1-1로 해소

`POST /api/auth/verifications`는 인증이 필요 없는 공개 엔드포인트이므로 누구나 직접 호출할 수 있다.
메일 링크를 **클라이언트가 보낸 값으로 조립**하면, 공격자가 `redirectPage`에 외부 주소를 넣어
피해자에게 **우리 도메인에서 정상 발송된 진짜 메일**을 보내게 만들 수 있다. 위조가 아니므로 메일 필터에도 걸리지 않고,
피해자가 링크를 열면 **유효한 인증 토큰까지 공격자 서버에 남는다.**

`redirectPage`를 폐기하고 백엔드가 origin만 쓰기로 하면서 이 경로 자체가 사라진다.
origin은 CORS 허용목록에 등록된 서버 소유 값이라 클라이언트가 개입할 여지가 없다.

### 운영 환경 API 문서 노출

`orval.config.js`가 `/v3/api-docs`에서 스펙을 가져온다. 개발에서는 필요하지만,
운영 프로필에서도 열려 있으면 전체 API 경로와 DTO 필드가 공개된다.
운영에서는 닫는 것으로 정리(`springdoc.api-docs.enabled=false` 또는 프로필 분리).

### 20자 초과 구글 `name`

백엔드에 길이 검증이 없어 현재 **OAuth 가입 자체가 실패**한다. 백엔드 `task-95`에서 잘라내기로 처리 예정.
가입 실패가 리다이렉트 이전에 발생하므로 프론트가 대응할 지점은 없다. 처리 후 회귀 확인만 한다.
