# Task 44: 화면 상태 정합성 — 실패와 낡음 처리

> 미착수. Task 42(실패 정규화) 완료가 전제다.

## 문제

화면이 실제와 다른 상태를 사실처럼 보여주는 경우가 둘 있다.
증상은 달라 보이지만 **"화면이 거짓말을 한다"는 같은 문제**이고, 해법도 같다 — 다시 가져오기.

| | 어긋남 | 사용자가 보는 것 |
|---|---|---|
| **A. 실패를 빈 화면으로** | 조회 실패인데 빈 배열 반환 | "참여중인 Flag가 없습니다" |
| **B. 낡은 화면 유지** | 409인데 문구만 띄움 | 이미 무효한 초대가 목록에 그대로 |

### A — 조회 실패 15곳

```ts
catch { return { success: false as const, data: [] as FlagResult[] }; }
```

```
flag.ts:21,31,44,54,159,169,236,248,290
buzz.ts:21,134   label.ts:15,27   notification.ts:15   social.ts:100
```

사용자는 빈 화면을 사실로 믿고, 재시도할 방법도 뭔가 잘못됐다는 신호도 없다.
`{ silent: true }`가 붙은 곳은 로그조차 남지 않는다.

Task 41 검증에서 실제로 이 함정에 걸렸다. 프로필의 최근 Flag가 비어 보였는데
화면만으로는 "조회 실패"인지 "그 친구에게 Flag가 없음"인지 알 수 없어,
API를 직접 호출해서야 후자임을 확인했다.

### B — 409를 문구로만 처리

409 Conflict는 **"당신이 보고 있는 데이터가 이미 바뀌었다"**는 뜻이다.
안내를 읽은 뒤에도 화면은 여전히 틀린 상태다. Task 41에서 확인된 사례:

| 상황 | 지금 |
|---|---|
| 종료된 Flag에서 참여 취소 | 문구 표시. 참여자 목록은 그대로 |
| 만료된 초대 수락 | 문구 표시. **초대 카드가 목록에 남아 다시 누를 수 있다** |

## 왜 하나로 묶는가

A의 **재시도**와 B의 **재조회**는 같은 장치다. 따로 만들면 두 벌이 되고
모양이 어긋난다. 대상도 겹친다 — Flag 상세 화면은 A(댓글·메모리얼 조회 실패)와
B(참여 취소 409) 양쪽에 걸린다.

## 방향

`ApiError.kind`와 `status`로 갈라 화면이 다르게 반응한다.

| 상황 | 화면 |
|---|---|
| `kind: network` · `timeout` | "연결을 확인해 주세요" + **재시도** |
| `kind: http` · `parse` | 사유 표시. 재시도는 상황에 따라 |
| 성공 + 빈 배열 | 지금의 빈 상태 문구 (진짜 "없음") |
| `status: 409` | **재조회 → 화면 갱신 → 그다음 안내** |

## Phase 구성

회귀가 났을 때 원인을 가릴 수 있도록 장치와 적용을 나눈다.

1. **재조회·재시도 장치** — 공통 UI 프리미티브를 먼저 만들고 커밋
2. **A 적용** — 조회 실패 15곳을 `kind` 기반으로 전환
3. **B 적용** — 409 재조회. 선행 확인(아래)이 끝난 뒤 마지막에

B를 마지막에 두는 이유는 아래 미확인 항목이 A의 착수를 막지 않게 하기 위해서다.

## 착수 전 결정할 것

**실패 상태 UI 패턴.** 액션만 고쳐서는 끝나지 않는다 —
전체 화면인지 인라인인지, 재시도 버튼을 어디 두는지,
**부분 실패**를 어떻게 표현하는지 정해야 한다.

특히 [app/page.tsx](src/app/page.tsx)는 `Promise.all` + 개별 `.catch()`로
여러 조회를 병렬 처리한다. 하나만 실패했을 때의 표현이 별도 설계 대상이다.

## 미확인 사항 (Phase 3 선행)

**모든 409가 "재조회하면 해결"인 것은 아니다.** 409를 내는 엔드포인트와
각각의 의미를 먼저 정리해야 한다 — "이미 처리됨"과 "상태가 안 맞음"은 대응이 다를 수 있다.

`code`(예외 클래스명)로 구분하고 싶어질 수 있으나 **그 방향으로 가지 않는다.**
클래스명은 계약이 아니라 구현 세부다(Task 42 참고). 구분이 정말 필요하면
백엔드에 안정적인 code 계약을 요청한다.
